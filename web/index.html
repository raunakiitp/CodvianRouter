How it works

The prompt is embedded once with the same deterministic hashed bag-of-words embedding as the semantic cache (token unigrams + bigrams into 256 buckets), then cosine-matched against 15 built-in example utterances per tier — coding, chat, reasoning, quick Q&A. Those utterances are config defaults, not measured traffic: they are the examples the matcher compares against. The tier with the highest score wins when it clears the threshold; otherwise the router falls back to the strong tier and says so. Scores are token-overlap similarity (0–1), not a quality judgement — paraphrases with different words score low, and that is exactly what the fallback is for.

Every decision reports its measured latency (embed + score only). Virtual models are also listed by GET /v1/models, and every auto-routed response carries X-Codvian-Auto-Tier, X-Codvian-Auto-Confidence and X-Codvian-Auto-Model headers.

How it works

A coalescable request is keyed on its canonical hash — model + messages + sampling params (max tokens, temperature, top-p, stop). The first request for a key becomes the leader: its whole retry loop (fallback, 429 backoff, hedging) runs once inside the flight. Identical requests arriving while it is in flight wait and share the leader’s result, success or failure; a shared failure reaches every waiter as the one error it was. The entry is registered before the leader dials, so a duplicate can never slip in as a second upstream call.

Streaming requests never coalesce (a stream cannot be shared between callers), and neither do tool-using or tool-call turns — a shared answer holds content only and must never silently drop tool calls. Usage accounting stays honest: the leader’s upstream attempt is the only one billed, and each waiter is recorded in the ledger as a shared row with zero tokens and zero cost. Counters come from GET /dashboard/coalescing and the same shared count is exposed as codvian_router_coalesced_total on the auth-gated /metrics.

Concurrency & TCP Fast Open

Adaptive per-provider concurrency limits (Gradient2): a provider that slows gets a smaller in-flight cap, so new calls shed to healthy providers before its queue grows and before 429s appear. The limiter fails open — it can only refuse a provider whose RTT has actually degraded.

How it works

Each provider gets its own in-flight cap, starting at 20 (floor 2, ceiling 100). Every successful call feeds its RTT into a Gradient2 estimate: cap = cap × (baseline RTT ÷ smoothed RTT) + 1. When a provider slows, its gradient drops below 1 and the cap shrinks within a few calls; the router then tries healthy providers first and only admits the slow one up to its reduced cap. When it recovers, the cap grows back gradually. Failed calls never move the estimate — a fast 429 says nothing about serving speed. Streaming calls hold a slot for the stream’s duration but never feed the RTT estimate (a stream’s wall time is not a serving RTT).

TCP Fast Open only pays on cold or failover dials: warm HTTP/2 pools are the primary defence, and the early data on a repeat dial is the TLS ClientHello, which TLS itself handles — the router never carries a request body in early data. A first-ever connection to a host still does a normal handshake to obtain a TFO cookie. Numbers come from GET /dashboard/concurrency; the same cap is exposed as codvian_router_concurrency_limit{provider} and shed calls as codvian_router_concurrency_rejected_total{provider} on the auth-gated /metrics.

On localhost the measured cold-dial difference is within noise (medians under a millisecond either way) — TFO saves up to one RTT, which only matters when the RTT is real.

Route guards

Every admin/management route is classified into one of three static tiers, evaluated before any other auth branch. Tier 1 routes can spawn processes or execute runtime code, so they answer only to loopback callers — a leaked key over a non-loopback connection still cannot reach a spawn.

How it works

Evaluation order: (1) Tier 1 loopback check, by the real TCP peer address (RemoteAddr) — the Host header and X-Forwarded-For are never consulted, because either can be forged; a non-loopback caller gets 403 LOCAL_ONLY before auth runs. (2) Tier 2 auth: a gateway key is always required, even when Tier 3 auth is relaxed. (3) Tier 3 auth, or anonymous when explicitly off. There is no manage-scope bypass: unlike OmniRoute, no privileged key can reach a Tier 1 route from off-host, and loopback alone is not enough either — a valid key is still required after the loopback check passes (except bootstrap, where no key exists yet).

A 403 LOCAL_ONLY in the logs is the guard working as designed, not an error to suppress. Fresh-install bootstrap (POST /admin/bootstrap) is loopback-only the same way and works exactly once, while no gateway key exists. The Tier 1 routes marked “not implemented yet” return 501 on loopback — they are classified local-only today so the feature lands guarded, not exposed. DB export/import/wipe have no route in this build, so there is nothing to call and nothing to protect; when they land they must be registered Tier 2 (and Tier 1 if they spawn a helper). The settings export never includes secrets — provider keys and gateway-key hashes stay on disk. Numbers come from GET /dashboard/guard.

If you run the router behind a reverse proxy or tunnel, never “fix” a 403 by forging the client IP as loopback — that re-opens exactly the remote-code-execution class this tier closes.
