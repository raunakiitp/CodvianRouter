# Codvian Router — Config Schema (v1)

The router reads its configuration from a single JSON file (default
`~/.config/codvian-router/config.json`). This document is the authoritative
description of version 1 of that file. The code that implements it lives
in `internal/config/config.go`; if this document and the code ever
disagree, the code wins and this document must be fixed.

## Top-level fields

| Field | JSON name | Type | Required | Default | Constraints |
|---|---|---|---|---|---|
| Version | `version` | integer | yes | `1` | Must be exactly `1`. Any other value is rejected on load. |
| Listen | `listen` | string | yes | `"127.0.0.1:20128"` | `host:port`. The host must be a loopback IP (`127.0.0.1` or `::1`); the router is local-only and never binds `0.0.0.0` or a LAN address. The port must be present and in range 1–65535. |
| DataDir | `data_dir` | string | yes | `~/.local/share/codvian-router` | Must not be empty. Created with mode `0700` if missing. |
| GatewayKeys | `gateway_keys` | array of gateway-key objects | no | `[]` | Each entry: `id` (string, unique), `name` (string), `key_hash` (hex SHA-256 of the raw key — the raw key is never stored), `scopes` (array of strings), `budget_usd` (number, ≥ 0), `created_at` (RFC 3339 timestamp), `guardrails` (array of strings, optional — CHECKLIST 245): the guardrail names that must guard this key's requests; every name must be registered — a built-in kind (`pii`, `secret`, `injection`) or a configured external guardrail name (`guardrails.external[].name`). An unknown name fails at load (and at key-update time), naming the key and the name. An empty/absent list names no guardrail: the key is guarded by the global blocking config exactly like a key without the field. Duplicate `id` values are rejected by `ValidateFile`. See `gatewaykey.go`. |
| Providers | `providers` | array of provider objects | no | `[]` | Each entry is a `provider.ProviderConfig`: `id` (string, unique, non-empty), `name` (string), `base_url` (string, non-empty, unique after normalization), `api_key_encrypted` (string, sealed value — never plaintext), `wire_format` (string), `models` (array of `{id, name, context_window?, input_price_usd?, output_price_usd?, fixed_params?, region?}`, optional), `enabled` (boolean), `quota_hint` (number), `created_at` (RFC 3339 timestamp), `region` (string, optional — CHECKLIST 257): the operator-declared serving region for this provider (e.g. `us-east-1`), the fallback for models that declare no region of their own; a model-level `region` wins over it. `""` (absent) means unknown — never a default, never inferred from the base URL or the provider's name, and never verified against a vendor's region list; a value with whitespace is rejected on load, naming the field. Failover tries the same model in another declared region before switching models (see `routing.model_equivalents`). `no_training_data` (boolean, default `false`): the operator's assertion that this provider does not use request data for training — what the per-request `routing.data_collection: "deny"` contract trusts (see CHECKLIST 157). Absent means "not verified", and `deny` excludes the provider rather than guessing it safe; local providers (catalog category `local`, or a loopback base URL) are safe by construction whether or not this is set. `fixed_params` (object, optional — CHECKLIST 245): the admin deployment pin for one model — `temperature` (number in [0, 2]), `top_p` (number in (0, 1]), `max_tokens` (integer ≥ 1). A set pin always wins over the client's body field for that model (the response carries `X-Codvian-Deployment-Override` naming the applied fields); an unset pin leaves the client's value alone. Out-of-range pins are rejected on load, naming the field. Duplicate `id` values and duplicate `base_url` values (after normalization) are rejected by `ValidateFile`. |
| BudgetUSD | `budget_usd` | number (float) | no | `0` | Global spend cap in USD. `0` means no cap. Must not be negative. |
| FailClosed | `fail_closed` | boolean | no | `true` | When `true`, the router refuses work instead of bypassing limits when a check cannot be performed. |
| AllowClientVertexOverride | `allow_client_vertex_override` | boolean | no | `false` | Admin opt-in for client-supplied Vertex location/project overrides (CHECKLIST 245). Default `false`: a request body carrying `vertex_location`, `vertex_project`, `vertex_ai_location` or `vertex_ai_project` is rejected with a 400 naming the field, before any provider is dialled. `true` admits the field; it still has no routing effect in this build — no Vertex provider consumes it — the location/project always come from the admin's provider config. |
| TelemetryEnabled | `telemetry_enabled` | boolean | no | `false` | No telemetry is ever sent unless this is explicitly `true`. |
| AutoRouter | `auto_router` | object | no | `{threshold: 0.5, default_tier: "reasoning"}` | Local auto-router (`auto/*` virtual models). `threshold` (number, 0 = default 0.5, otherwise in (0, 1]): a tier match below it falls back to the default tier instead of guessing. `thresholds` (object, virtual-model name → number in (0, 1]) overrides the threshold per virtual model (`auto`, `auto/fast`, `auto/cheap`, `auto/coding`, `auto/reasoning`). `default_tier` (string, one of `coding`, `chat`, `reasoning`, `quick-qa`) is the fallback tier. `default_model` (string) is the concrete model used when the picked tier has no `tier_models` entry; empty means auto-routing fails honestly instead of inventing a model. `tier_models` (object, tier name → array of concrete model IDs in preference order) maps tiers to models. `intent_tiers` (object, intent tier name → `{model, effort?}` — CHECKLIST 259): the operator-defined meaning of each intent tier (`fast`, `balanced`, `best`) — a request naming `intent/<tier>` resolves to that (model, effort) pair with no classification; `effort` is `low`, `medium` or `high` (empty = no effort pinned); a tier with no entry is unmapped and a request naming it fails honestly naming the tier. Unknown tier names, empty models and unknown efforts are rejected on load, naming the field. `feedback_learned_weights` (boolean, default `false` = OFF): when `true`, per-tier score nudges learned from accept / edit / discard / regenerate signals (see `internal/feedback`) apply to routing — a tier gets no nudge until it has 10 signals, and the nudge is bounded to ±0.05; when `false`, signals are still recorded but the nudges are exactly zero, so routing is unchanged. `learned_router` (boolean, default `false` = OFF): when `true`, the learned auto-router (see `internal/learned`, RouteLLM pattern) predicts a per-tier win probability from the recorded heuristic scores and composes it into routing as a bounded (+/-0.05) additive signal — but it stays OFF until real evidence exists (at least 50 labelled outcomes and a held-out calibration error at most 0.15 with log-loss beating the base rate), so with no evidence routing is exactly unchanged. No keys are stored here — only model names. |
| Routing | `routing` | object | no | `{"deadline_budget_ms": 300000}` (global `balanced`, 300 s deadline budget, no overrides, cooldown `hard`) | Routing-strategy family (31 names: `priority`, `balanced`, `cheapest`, `fastest`, `most-reliable`, `least-latency`, `weighted`, `custom-weights`, `code`, `round-robin`, `random`, `strict-random`, `fill-first`, `least-used`, `p2c`, `quota-weighted`, `headroom`, `expiry-first`, `reset-aware`, `reset-window`, `lkgp`, `context-optimized`, `cache-optimized`, `context-relay`, `cost-optimized`, `ship-fast`, `cost-saver`, `quality-first`, `offline-friendly`, `reliability-first`, `chaos-mode`). `global_strategy` (string, empty = `balanced`): the default strategy for every chain. `deadline_budget_ms` (integer, ≥ 0, 0 = disabled; fresh-config default 300000 = 5 min, RT-1): the per-combo time budget — when spent, the combo stops with `ErrDeadlineExceeded` (clean 504) instead of burning more attempts. An explicit 0 disables the budget. A config file with no `routing` block (or no `deadline_budget_ms` in it) still loads with no budget — `Load` applies no defaults to an existing file, so a pre-RT-1 file stays unbounded until the operator adds the field (see `config.go:3486`). `stream_max_lifetime_ms` (integer, milliseconds, 0 = 30-minute default, negative = cap disabled — CHECKLIST 255): the hard lifetime bound on a held or relayed stream — on expiry the upstream call is terminated and the client gets a clean terminal event carrying the stream-lifetime error, never a silent close. `media_timeouts_ms` (object, endpoint name → integer milliseconds, 0 = default, max 3,600,000 = 1 h — M8.20 F3): the per-endpoint request timeout for the media surfaces — keys `search`, `ocr`, `video` (covers both the video-generations POST and the video-task GET) and `music`; an unset key (or 0) means the default, 10 minutes for `music` (MiniMax generation is synchronous and takes tens of seconds to several minutes, with no provider-documented upper bound, so 10 minutes is a chosen operator-overridable bound) and 120 s for the other endpoints; unknown keys, negative values and values above 1 h are rejected at load. `chain_strategies` (object, model ID → strategy name): per-chain override; a chain with no entry inherits the global strategy, and a per-request `auto:<axis>` alias still wins over both — and a per-request `routing.sort` contract wins over the alias (precedence: contract sort > alias > chain > global; see CHECKLIST 157). `strategy_tree` (object, a nestable strategy tree for every chain) and `strategy_trees` (object, model ID → tree; the per-chain tree wins over the global tree for its model): a node is `{strategy, children[]}` (an internal node that picks among its children by its strategy) or `{provider, model?}` (a leaf naming one provider, optionally pinned to one model) — e.g. cheapest-of[fastest-of[A, B], C] (see CHECKLIST 177). Each node picks among its children by its strategy and the full ordered list of each child follows its winner; attempts no leaf names are still tried afterwards, never dropped. A per-request contract `order` skips the tree entirely (the client's try order is final); a contract `sort` or an `auto:<axis>` alias replaces only the tree root's strategy. Nesting is capped at 8 nodes deep and a cycle is rejected at load, both naming the node path (`root.children[0]...`); unknown strategies, leaves without a provider, and nodes that are both picker and leaf are rejected at load too. `weighted_weights` (object, `latency`/`success`/`cost`/`quality`/`quota`, each in [0, 1]): the custom 5-factor weights for the `custom-weights` strategy (alias `custom`), normalised to sum to 1 at use; all-zero means no custom weights (`custom-weights` behaves as `balanced`). (Pre-1.0 rename, M3: `weighted` is now the per-target weight draw — see `chain_weights`.) `chain_weights` (object, model ID → object, `provider/model` → weight, each finite and ≥ 0): the per-target weights for the `weighted` strategy's draw — a target's share of draws is its weight over the chain total (e.g. 3 vs 1 means ~75% of draws); a weight of 0 excludes that target while any positive weight exists; a chain whose weights are all zero is rejected at load; a chain with no entry draws uniformly. `cooldown_mode` (string, empty = `hard`): the global cooldown mode for retryable failures — `hard` skips a cooling provider until its cooldown ends, `soft-demote` moves it to the end of the order instead (still tried once per request). `chain_cooldown_modes` (object, model ID → `hard` / `soft-demote`): per-chain override; a chain with no entry inherits the global mode. Unknown cooldown modes are rejected on load, naming the field. `account_fallback_strategy` (string, empty = `fill-first`): the global account-level fallback strategy — how the accounts (keys) of one provider serving one model are ordered when a request falls back between them. `account_fallback_strategies` (object, provider ID → strategy name): per-provider override; a provider with no entry (or an empty value) inherits the global value. Valid values (9): `priority`, `fill-first`, `round-robin`, `p2c`, `random`, `least-used`, `cost-optimized`, `strict-random`, `weighted` — unknown names are rejected on load, naming the field and value. `expiry-first` is rejected: no per-key quota-expiry source exists, so it can never order accounts honestly (design §D2). `weighted` draws uniformly (all weights 1) until a per-account weight source exists; `p2c` at account level is a random draw with a breaker guard (accounts of one provider share the provider-level score). Default `fill-first` (the reference router's default). `sla` (object, all fields optional; absent = defaults 2000 ms / 5% errors / no cost cap / soft constraints): the operator's SLOs for the `sla-aware` strategy — `target_p95_ms` (number, > 0 when set): the latency objective in milliseconds; `max_error_rate` (number, in [0, 1]): the tolerated error fraction — an explicit 0 is zero-tolerance (any measured error violates the SLO), while an absent field means the 0.05 default; `max_cost_per_1m_tokens` (number, ≥ 0): the blended-cost cap in USD per 1M tokens — 0 means no cap, the same as absent; `hard_constraints` (boolean): when true, fewest SLO breaches win and score breaks ties, instead of highest score winning. A non-positive target, an error rate outside [0, 1], or a negative cost cap is rejected at load, naming the field. Honest limitations: the latency actually fed to the scorer is the measured p50 EWMA standing in for p95, not a true p95 (no latency histogram exists yet — true p95 and latency stddev are deferred, and stability scores neutral 0.5); candidates whose circuit breaker is positively known OPEN are filtered before scoring, and only when every candidate is OPEN is the full pool scored (the reference router's rule). `nadir` (object, all fields optional; absent = unconfigured): the decision-endpoint settings for the `nadir` strategy — `endpoint` (string, empty = unconfigured): the origin of a Nadir-compatible decision API (e.g. `https://api.getnadir.com`); a trailing `/v1` is stripped, so a pasted base URL cannot double up to `/v1/v1/bucket`. `timeout_ms` (integer, 0–30000, 0 = the 2000 ms default): the bound on one decision call; the engine (for programmatic config) clamps values above 30000 to 30000. A non-http(s) endpoint, a negative timeout, or a timeout above 30000 is rejected at load, naming the field. There is no API-key field: the key comes from the `CODVIAN_ROUTER_NADIR_API_KEY` environment variable only, and empty means no `X-API-Key` header is sent. There is no default endpoint and no env fallback for the endpoint (a deliberate divergence from the reference router's fail-open hardcoded `https://api.getnadir.com`): unconfigured means `auto/nadir` falls back to priority order and NEVER calls any external API. WARNING — egress: when an endpoint IS configured, every `auto/nadir` request sends the prompt's last user turn (capped at 16,000 chars) plus the pool's model ids (max 100) to that endpoint in one `POST /v1/bucket`; after a failed decision call the endpoint is skipped for 30 s (failure cooldown) instead of being retried on every request. `refusal_chains` (object, model ID → array of provider IDs, in order): the content-policy refusal chain for that model — the targets tried once each, never the refusing target again, when a target refuses the content on policy/safety grounds; a model with no entry uses the default (the failure chain's remaining targets, each once), and an explicitly empty list means no refusal routing for that model (the first refusal ends the request in an honest 403 / -32001 at once). Provider IDs must be non-empty with no duplicates in one chain; a name with no live client is skipped at request time, never dialled. `context_fallback_models` (array of model IDs, in preference order): the dedicated context-window fallback chain — when a prompt does not fit any model in the requested chain (local token count + response reserve vs the model's context window), the request jumps straight to these long-context models instead of retrying the too-small ones; empty means no dedicated chain and a prompt that fits nothing fails honestly pre-call (400, no provider called). `model_equivalents` (object, model ID → array of model IDs, in preference order — CHECKLIST 257): the operator-declared equivalent models failover may try after the same model in another region and before any self-hosted model; equivalence is never guessed from a name, a price, or a benchmark. A model with no entry has no equivalents; an entry no provider offers contributes nothing; a model listing itself or repeating a model is rejected on load, naming the field. `context_reserve_tokens` (integer, ≥ 0, 0 = default 4096): the response reserve held back when the caller did not set `max_tokens`; a request `max_tokens`, when set, replaces it for that request. `groups` (object, group name → array of provider IDs, in order): user-named routing groups (CHECKLIST 173) — a group is one named routing target, addressed by name in a request (`routing.group`, or the `group:<name>/<model>` model alias) or as a `group:<name>` entry in a `refusal_chains` list, and resolves to its members in order, participating in failover, budgets and the ledger exactly like a chain. Group names must be non-empty and must not contain `:` or `/`; a group must list at least one provider; every member must be a provider ID from this config file (an unknown member is a startup error naming it) with no duplicates in one group. A member may carry a reasoning effort as `provider@low` (CHECKLIST 255): a group entry is (model, effort), so the same provider twice at different efforts is two distinct entries and the duplicate rule is on the (provider, effort) pair; an unknown effort level is rejected at load, naming it. At request time a member with no live client, a disabled member, or a member that does not offer the requested model is skipped; a group whose members all skip for a model fails the request honestly with a 400 naming the group and the model. A `refusal_chains` entry starting with `group:` expands to the group's members for that model, and the group name is validated at load (an unknown group is a startup error naming it). `fusion_judge_model` (string, empty = the first panel member — the fusion default): the model the `fusion` strategy uses as its LLM judge; when set it must be servable, and an unresolvable judge model falls back to the first panel member, never to a guess. `fusion_min_panel` (integer ≥ 0, 0 = 2): the minimum number of successful panel answers before the judge synthesizes — a panel below it is served directly (the best survivor's verbatim answer, no judge call). `fusion_max_panel` (integer ≥ 0, 0 = 40): the panel size cap. `fusion_straggler_grace_ms` (integer ≥ 0, 0 = 8000): how long a slow panel member may keep the panel open after the others answered. `fusion_panel_hard_timeout_ms` (integer ≥ 0, 0 = 90000): the hard wall-clock cap on the whole panel. Negative values are rejected at load, naming the field, and `fusion_min_panel` above `fusion_max_panel` is rejected too. `jev_judge_enabled` (boolean, default `false` = OFF — A2-4): when `true`, the JEV strategy's System One scoring runs through a real LLM judge call to the configured judge model instead of the deterministic heuristic scorer; when `false` (the default) the preference order is unchanged — heuristic scorer, no judge call. `jev_judge_model` (string, empty = no judge model): the model the JEV judge call is sent to (resolved through the engine's chain map, like a routing-group model). Even with `jev_judge_enabled` on, an empty `jev_judge_model` (or a model with no serving chain) skips the judge call and uses the heuristic scorer; a judge failure always falls back to the heuristic scorer, so a request never fails because the judge did. The JEV judge never calls any vendor decision API. A `qtSd/<group>/<provider>/<model>` model alias (A2-5) addresses a routing group directly as a quota-share pool: the group expands to its provider/model chain and the request is routed through it with the `quota-share` strategy (the engine's DRR orders the members by their configured share from `routing.quota_shares`; a pool with no shares table shares evenly), then the alias is unwrapped to the real targets — the request model becomes `<provider>/<model>` and the group's chain is the routing chain. An unknown pool, or a pool with no member serving the model, fails with a 400 naming it; a non-qtSd model is untouched. |
| Pools | `pools` | object | no | `{}` (defaults: 20 req/s × 1000 ms → 20 idle) | Warm HTTP/2 connection pools, one per (provider, key) — see `docs/pool-sizing.md` and `internal/provider/pool.go`. `expected_rps` (number, ≥ 0, 0 = default 20): the mean request rate λ the pool is sized for. `expected_latency_ms` (number, ≥ 0, 0 = default 1000): the mean time W a request holds a connection, in milliseconds. `max_idle_per_host` (integer, 0–1000, 0 = derive): explicit pool size override — the derived size is `N = ceil(expected_rps × expected_latency_ms / 1000)`, clamped to [`min_conns`, `max_conns`]. `min_conns` (integer, ≥ 0, 0 = default 2): floor. `max_conns` (integer, ≥ 0, 0 = default 200): ceiling. A ceiling below the floor is rejected on load, naming the field. |
| Prices | `prices` | object (model ID → price object) | no | `{}` (no model priced — every model unknown) | **The operator-configured price source** (see `prices.go`). Each entry is a price object: `input_usd_per_1m` (number, ≥ 0, USD per 1M input tokens), `output_usd_per_1m` (number, ≥ 0, USD per 1M output tokens), `cached_input_usd_per_1m` (number, ≥ 0, optional: USD per 1M cached-input tokens). A field that is absent means "unknown" — it is never treated as 0; a field set to `0` means genuinely free. A model with no entry, or with only one of input/output set, has an unknown blended price (the scorer treats it as neutral, never cheapest; the ledger records $0). Negative, NaN or infinite values are rejected on load, naming the model and field. Prices are never fetched from the network and never invented: the only sources are this block and `price_file` — plus the separate opt-in `models_dev` sync, which fills in ONLY pairs the operator has not priced at either level and is always consulted last (see `docs/models-dev-sync.md`). |
| PriceFile | `price_file` | string (local path) | no | `""` (no price file) | Optional local JSON price file with the same shape as `prices` (a flat object: model ID → price object). Read once at startup; a missing or invalid file fails startup. Entries from the file are overridden by the same model in `prices` (config file wins). |
| ModelsDev | `models_dev` | object | no | `{}` (sync OFF) | **Opt-in live price/context sync from models.dev** (see `docs/models-dev-sync.md`). `enabled` (boolean, default `false` = OFF): with it off the router never contacts models.dev. `url` (string, empty = `https://models.dev/api.json`): the catalog URL — http(s) only, validated on load whether or not the sync is enabled. `interval_minutes` (integer, ≥ 0, 0 = once at startup only): re-sync cadence. `timeout_seconds` (integer, 0 = default 15s, otherwise 1–120): one fetch bound. When on, the router fetches the public models.dev catalog and fills in prices (USD per 1M tokens, base tier only — tiered prices are ignored) and context windows ONLY for (provider, model) pairs the operator has NOT priced (pair or model-level) and windows the operator has NOT set; operator values always win, and a pair the operator prices later drops out of the synced layer on the next sync. A failed/offline fetch keeps the last good data and records the failure (last error + last success time, shown on the dashboard Models view); the synced state persists in `models-dev-sync.json` in the data dir. |
| Compression | `compression` | object | no | `null` (no compression) | Lossless-first prompt compression (see `docs/compression.md`). `lossless_models` (array of model IDs, no empty entries, no duplicates): models whose prompts are losslessly compressed — duplicate system/developer blocks, redundant whitespace, stale tool results — even when the request does not opt in. A request's `"compression":{"lossless":false}` opts out for that call. There is no lossy setting here: lossy trimming is per-call only (`"compression":{"lossy_max_prompt_tokens": N}` in the request body) and is always disclosed in response headers, the route trace, and the ledger. |
| Guardrails | `guardrails` | object | no | `null` (all toggles off, no external guardrails) | Guardrail stage (see `docs/async-guardrails.md`). `block_pii` / `block_secrets` / `block_injection` (booleans): refuse requests (and non-streaming responses) matching PII, secret, or prompt-injection patterns with 403 / `-32001` before any provider is dialled. Log redaction is always on and is not a config value. `external` (array of external-guardrail objects, optional): one entry per slow external classifier — `name` (string, unique, non-empty), `kind` (string, the verdict label), `mode` (`"sync"` or `"async"`), `endpoint` (string, valid http(s) URL), `timeout_ms` (integer, ≥ 0, 0 = 5 s default). `sync` checks before dialling; `async` checks concurrently with the provider call (a BLOCK verdict cuts a live stream with the same 403 / `-32001` refusal frame, or withholds a non-streaming response). An async entry with a blocking kind (`pii`, `secret`, `injection`) is rejected at load, naming the guardrail — a secret must never reach a provider while a verdict is in flight. Duplicate names, unknown modes and bad endpoints are rejected at load the same way. |
| Responses | `responses` | object | no | `null` (counting-only) | Responses API (`/v1/responses`, see `docs/responses-api.md`). `session_token_cap` (integer, ≥ 0, 0 = counting-only — CHECKLIST 263–264): the per-session token cap for Responses continuations — a session whose counted tokens plus the next turn's prompt estimate would exceed it refuses the turn with 429 (`session_token_limit`) before any provider is dialled. `0` (or an absent `responses` block) means turns are counted and reported on the dashboard, never refused. A negative value is rejected on load, naming the field. The cap is read at startup; changing it needs a restart. |
| Plugins | `plugins` | object | no | `null` (no plugins) | In-process plugin registry (see `docs/plugins.md`, CHECKLIST 201). `enabled` (array of strings, in order = pipeline order) names built-in plugins to run: `header-add` (adds `X-Codvian-Plugin: header-add` to every upstream request) and `response-log` (records model, finish reason, content length and token counts per delivered response — never content). Unknown names, empty entries and duplicates are rejected at load, naming the entry. There is deliberately no path / URL / `.so` field: plugins are compiled-in Go code only, never arbitrary code loaded from config; `POST /admin/plugin/load` answers 501 by design. |
| Shortlist | `shortlist` | array of strings | no | `[]` (no shortlist — the catalog lists in registry order) | Curated model shortlist (CHECKLIST 199-200): model IDs pinned to the top of the catalog in list order, clearly marked (`shortlisted: true`) in `GET /v1/models` and `GET /dashboard/models`. An entry pins any row whose model ID equals the entry (`"gpt-4o"`, matched wherever it is offered) and any row whose `"providerID/modelID"` equals the entry (matched only for that provider) — both readings of an entry containing `/` apply, so a model ID that itself contains `/` keeps working as a plain pin. Entries must be non-empty with no duplicates (rejected on load); entries naming models no provider offers are ignored, never an error — the shortlist is a display pin, not a routing rule. |
| MCP | `mcp` | object | no | `null` (no MCP servers — chat completions flow exactly as before; the dashboard's MCP section reports the honest empty state) | MCP selector mode (see `internal/mcptools`, CHECKLIST 141, M9.6). `mode` (string, empty = `"selector"`): `"selector"` injects only the two meta-tools `mcp_tools_get` / `mcp_tools_execute` no matter how many servers or tools are configured; `"direct"` (opt-in) injects every discovered tool schema. `max_iterations` (integer, 0 = default 10, highest accepted 50): caps the agent loop's follow-up model calls per request — hitting the cap stops the loop honestly instead of looping forever. `servers` (array of server objects): one entry per external MCP server — `name` (string, unique, prefixes every tool it exposes as `server__tool`), `command` (string, the executable to spawn), `args` (array of strings). A server that fails to start or answer `tools/list` is logged and recorded as down and contributes no tools; the healthy servers still load. `controls` (object, optional — M9.6 client-side hardening, see `internal/mcptools/controls.go`): presence is the switch. Absent (`controls` missing) means legacy behaviour — the registry is built with `mcptools.New`, allow-all, exactly as before M9.6; this does not touch the server-side M9.1 scopes, which are enforced on the router-as-server side regardless. Present (even empty, `"controls": {}`) means enforced, fail-closed, from construction via `NewWithControls`: an empty `allow` list denies every tool, and a present-but-empty block is a deliberate deny-all, not a mistake, and is not rejected on load. Fields: `allow` (array of strings, glob patterns matched against `"server__tool"` — `"calc__echo"`, `"calc__*"`, a plain tool name matches any server, `"*"` matches all; a tool executes only if some `allow` pattern matches AND no `deny` pattern matches); `deny` (array of strings, same pattern form — a `deny` match wins over any `allow` match; the check runs BEFORE dispatch, so a denied tool never reaches the server); `max_calls` (integer, 0 = unlimited): at most that many dispatched tool executions per budget window — the N+1th call is refused before dispatch; the budget reservation is made before dispatch and is NOT refunded when the server call fails, so a failed dispatch counts as one spent call; `max_duration` (Go duration string, e.g. `"5m"`, `"30s"`, `"1h30m"`, or a JSON number of nanoseconds — the `encoding/json` shape of `time.Duration`; a string is the form operators write, the number form stays accepted so a file written from a marshalled `mcptools.Controls` still loads): the wall-clock budget for the window, measured from when controls were engaged (or the last `ResetBudget`); a call that starts after the budget is spent is refused before dispatch; 0 = unlimited. Both spend caps are enforced in the single `ExecuteDetailed` choke point, so no caller can bypass them. There is NO dollar cap here: the MCP `tools/call` wire format carries no usage or price, so a plain tool server can never yield a cost (`CostEstimate` reports usage unknown); only a server implementing the optional `UsageReportingServer` interface reports token counts, and a USD figure only when the server itself reports one — no price table for external MCP tools exists anywhere, so `max_calls` / `max_duration` are the real, enforceable caps. An invalid `max_duration` (boolean, object, malformed string, non-integer number) is a load error naming the field, never silently ignored. |

Notes on "required": a missing field decodes to its Go zero value, and
`Validate` then rejects the file if that zero value is unsafe (for
example a missing `version` decodes to `0` and is rejected, and a missing
`data_dir` is rejected as empty). A missing `listen` is rejected because
it has no host or port. `gateway_keys` and `providers`, when absent, are
treated as empty lists. `fail_closed` absent decodes to `false` — callers
that create a config should use `DefaultConfig`, which sets the safe
defaults above, rather than hand-writing a partial file.

The file itself is written atomically (temp file + rename) with mode
`0600`.

## Unknown-field preservation

A v1 reader **preserves** any top-level field it does not recognise:

- On load, every top-level key outside the table above is stored, raw
  JSON bytes included, in `Config.Extensions`
  (`map[string]json.RawMessage`), keyed by its JSON name.
- On save, each entry is re-emitted as a top-level key with its raw
  value verbatim, so a Load → Save round-trip does not lose, rename, or
  reinterpret fields written by a newer (or older, or foreign) writer.
- `Extensions` itself is tagged `json:"-"`: it never appears as a field
  of its own in the file. If an extension key collides with a known
  field name, the known field wins and the extension entry is dropped
  on marshal.
- Unknown fields are **never validated or interpreted** by v1 code.
  They are opaque payload carried through, nothing more.

Example: a file containing `"future_feature": {"enabled": true}` loads
fine under v1, and after the router saves the config the key is still
there with the same value.

## Forward-compatibility promise

- **v1 readers ignore nothing they do not understand** — unknown fields
  survive round-trips, as above. A newer writer's extra fields are
  safe to carry through a v1 binary.
- A future **v2 will be a separate migration, not a silent
  reinterpretation**: it will use `version: 2`, v1 readers will reject
  it outright (unsupported version), and any upgrade path will be an
  explicit, documented migration step. The meaning of an existing v1
  field will never change under the v1 version number.
- The one thing v1 does *not* promise: unknown fields inside a
  *nested* object (for example an extra key inside one `providers`
  entry) are handled by that nested type's own decoding, not by
  `Extensions`, and may be dropped. Only top-level unknown fields are
  preserved.
